# v0.9.3 リリース阻害問題
## 加工場の実体化・導線・保存信頼性

このファイルに記載した項目は、新機能より優先します。

一つでも未達の場合、v0.9.3を完成扱いにしないでください。

---

# 1. 現在確認できる構造上の問題

## 1.1 加工ロジックは存在するが、ゲーム世界へ接続されていない

現在のコードベースには、次が存在します。

- 加工場用地の状態
- 製粉機・ベーカリーの状態
- レシピ
- 入力・出力バッファ
- 生産サイクル
- 加工スタッフ状態
- 加工方針
- 保存スキーマ

一方、`GameScene`は現在、次のシステムだけを生成・更新しています。

```text
MarketSystem
UpgradeSystem
WorkerSystem
HiringSystem
ExpansionSystem
ExpandedAutomationSystem
```

加工場を描画・購入・更新する専用ランタイムシステムがありません。

したがって、READMEや保存データに加工場が存在しても、プレイヤーが世界内で加工場を発見・購入・操作できない状態になり得ます。

v0.9.3では、純粋ロジックだけでなく、実際に次を結ぶ必要があります。

```text
施設表示
→ 前提条件表示
→ 購入操作
→ 建設状態
→ 機械操作
→ 生産サイクル更新
→ 倉庫・集配との資源移送
→ HUD
→ 保存
```

## 1.2 集配ネットワークも状態・純粋ロジックだけで終わらせない

v0.9.1では、集配ネットワークの状態・施設定義・純粋ロジックが追加されています。

v0.9.3では、次を実機で確認してください。

- 集配所を建設できる
- 各集配ボックスを建設できる
- プレイヤーが資源を預けられる
- 集配スタッフを雇用できる
- スタッフが実際に移動する
- 加工場受入ボックスへ資源が入る
- 加工不能時に倉庫へfallbackする
- 保存後に在庫・スタッフ状態が戻る

コード上の関数やstateが存在するだけでは、受入条件を満たしません。

## 1.3 保存検証が時間値へ整数を要求している

現在の保存検証では、在庫数・レベル・容量に使う整数判定と、経過時間・残り時間に使う数値判定が同じ関数で処理されています。

ゲームの`delta`やTween・タイマー由来の値は、小数ミリ秒を含むことがあります。

例：

```text
crop.remainingMs
machine.activeCycle.remainingMs
collectionNetwork.sourceAgesMs
courier.waitMs
playTimeMs
```

これらへ`Number.isInteger()`を要求すると、実プレイで作成した正常なスナップショットが保存後検証に失敗する可能性があります。

自動テスト用の整数fixtureだけでは、この問題を検出できません。

## 1.4 保存ボタンの結果が操作中の画面で分かりにくい

現在、管理メニューから「今すぐ保存」を押しても、保存結果は背景側の小さな保存状態表示へ出る可能性があります。

オーバーレイ内で明確に、次を表示してください。

```text
保存中…
保存しました
保存に失敗しました
保存先を簡易保存へ切り替えました
```

ユーザーが、ボタンを押した結果をその場で確認できなければなりません。

# 2. 加工場のランタイム実装

新しいシステムを作成してください。

推奨名：

```text
ProcessingSystem
ProcessingYardSystem
```

## 2.1 システムの責務

- 加工場用地の表示
- 閉鎖中ゲート
- 購入範囲
- 前提条件判定
- 購入進捗
- 製粉機建設
- ベーカリー建設
- 機械アップグレード
- 運転モード変更
- 入出力バッファ表示
- 生産サイクル更新
- 製粉スタッフ・製パンスタッフのruntime
- 集配受入ボックスとの仕分け
- 倉庫への完成品搬送
- HUD・接近案内
- priority save要求
- shutdown cleanup

`GameScene`はシステムを生成し、毎フレーム`update(delta)`を呼びます。

## 2.2 加工場の配置

既存の鶏小屋・集配所・東農地・研修小屋と重ならない位置へ置きます。

推奨配置：

```text
加工場用地：南東区画
x = 1950〜2850
y = 1280〜1840
```

ただし現在の集配所・加工場受入ボックスとの位置関係を確認し、実際のFacility Registryから非重複を検証してください。

加工場用地には次を置きます。

- 加工場入口
- 閉鎖ゲート
- 加工場管理看板
- 製粉機区画
- ベーカリー区画
- 加工場受入ボックス
- 完成品搬出口
- スタッフ待機位置
- 倉庫へ続く道

## 2.3 解放前から存在を認識できること

加工場用地を完全に非表示にしてはいけません。

未解放時でも、遠くから次を認識できる必要があります。

- 閉じた門
- 鍵のアイコン
- 「加工場予定地」の看板
- 道路の続き
- 次の目標マーカー

## 2.4 解放条件

加工場用地の購入条件：

```text
東農地を購入済み
鶏小屋を購入済み
所持金 800コイン以上
```

製粉機：

```text
加工場用地購入済み
350コイン
```

ベーカリー：

```text
製粉機建設済み
850コイン
```

条件不足時は無反応にしません。

表示例：

```text
加工場予定地

必要条件
✓ 東農地
✓ 鶏小屋
あと 230コイン
```

または、

```text
先に鶏小屋を購入してください
```

## 2.5 解放通知

東農地と鶏小屋が両方解放された瞬間に、一度だけ次を表示します。

```text
加工場を建てられるようになりました
```

同時に、次の操作を提供します。

```text
加工場へ案内
```

PC：

- 通知内ボタン
- 施設一覧から案内

スマートフォン：

- 大きなタップボタン

案内を押すと、次のいずれかを行います。

- 地面へ方向矢印を短時間表示
- カメラを一時的に加工場方向へパンして戻す
- 加工場予定地にパルスするマーカーを表示

プレイヤーを強制移動させないでください。

## 2.6 「次の目標」パネル

画面を圧迫しない小さな進行パネルを追加します。

例：

```text
次の目標
加工場を建てる
800コイン
```

状態に応じて切り替えます。

```text
東農地を購入
鶏小屋を購入
加工場用地を購入
製粉機を建設
ベーカリーを建設
牧草地を購入
牛舎を建設
乳製品工房を建設
```

設定で通常案内を非表示にしている場合でも、初回解放通知と施設の前提条件表示は維持してください。

## 2.7 実際の生産

製粉機・ベーカリーについて、少なくとも次を実プレイ可能にします。

```text
麦2 → 小麦粉1
とうもろこし2 → コーンミール1
小麦粉1＋たまご1 → パン1
小麦粉1＋コーンミール1＋たまご1 → コーンブレッド1
```

必要条件：

- 入力在庫が見える
- 出力在庫が見える
- 残り時間が見える
- 稼働／停止が分かる
- 原料不足が分かる
- 出力満杯が分かる
- 運転モードを変更できる
- 加工スタッフを雇用できる
- 完成品が倉庫または集配へ移る

# 3. 保存システムの修正

## 3.1 数値検証を分ける

次の関数を分離してください。

```ts
finiteNonNegativeInteger(value)
finiteNonNegativeNumber(value)
```

整数が必要：

- 資源個数
- コイン
- 容量
- レベル
- 完了回数
- 契約個数
- round-robin index

有限の非負数でよい：

- 残り時間
- 経過時間
- 待ち時間
- 作物成長時間
- 生産時間
- playTimeMs

保存前に時間値を整数ミリ秒へ正規化しても構いません。

推奨：

```ts
Math.max(0, Math.round(value))
```

migrationでは、小数時間値を失敗扱いにせず、正常化してください。

## 3.2 保存キュー

保存中に新しい変更が発生しても、最新状態が失われないようにします。

推奨状態：

```ts
saveInFlight: boolean
saveRequestedWhileBusy: boolean
latestSnapshotFactory: () => snapshot
```

保存中にpriority saveが要求された場合：

1. 現在の保存を完了
2. 最新スナップショットを再取得
3. もう一度保存

単に要求を捨てないでください。

## 3.3 saveSequence

ロード時に、グローバルな保存連番を0へ戻さないでください。

```text
sequence = loaded.payload.saveSequence
```

次回保存で、

```text
sequence + 1
```

とします。

## 3.4 IndexedDB fallback

IndexedDBが次の理由で使えない場合があります。

- プライベートブラウズ制限
- ストレージ権限
- ブラウザ実装差
- transaction失敗
- quota
- DB open失敗

次の二層構成を推奨します。

```text
Primary:
IndexedDB

Fallback:
localStorageの簡易セーブ
```

fallbackは、セーブデータが2 MiB未満の場合のみ使用します。

表示：

```text
保存先：ブラウザー保存
```

または、

```text
IndexedDBを利用できないため、簡易保存を使用しています
```

IndexedDBが次回利用可能になった場合、簡易保存を検証し、primaryへ移行できるようにしてください。

## 3.5 pagehide用緊急保存

`pagehide`や`visibilitychange`では、非同期IndexedDB保存の完了が保証されません。

通常保存とは別に、最後の正常な正規スナップショットをlocalStorageへ同期的に書く、緊急スナップショットを検討してください。

次回起動時：

1. primary確認
2. backup確認
3. emergency snapshot確認
4. 更新日時・連番を比較
5. 最も新しい正常データを候補として提示

自動的に古いデータで上書きしないでください。

## 3.6 手動保存UI

管理メニュー内に、保存結果を表示します。

```text
今すぐ保存

保存中…
保存しました　15:42:18
```

失敗時：

```text
保存に失敗しました
原因：データ検証エラー
```

技術的詳細は、開発者向けに折りたたみ表示またはコンソールへ出します。

ユーザーへは、次の行動を示します。

```text
もう一度試す
JSONとして書き出す
簡易保存へ切り替える
```

## 3.7 保存テスト機能

設定または管理画面へ、開発中だけでなく公開版でも利用できる次の機能を追加します。

```text
保存機能を確認
```

処理：

1. 現在状態を保存
2. repositoryから即時再読込
3. checksum検証
4. schema検証
5. 重要フィールド比較
6. 結果表示

成功：

```text
保存機能は正常です
保存先：IndexedDB
```

失敗：

```text
保存を確認できませんでした
JSON書き出しを利用してください
```

## 3.8 タイトル画面

正常なセーブがある場合：

```text
つづきから
最終保存日時
保存先
所持金
解放済み施設
```

セーブがない場合：

```text
はじめる
```

セーブが破損している場合：

```text
バックアップから復元
緊急保存から復元
JSONを読み込む
新しくはじめる
```

黙って新規ゲームを始めないでください。

# 4. 実機で保存を確認する必須シナリオ

自動テストだけでは完了としません。

GitHub Pages上で、次を確認します。

1. 新規ゲーム開始
2. コインを増やす
3. 東農地を購入
4. 手動保存
5. 「保存しました」がメニュー内に出る
6. ブラウザーを再読み込み
7. 「つづきから」が表示される
8. 続行
9. コインと東農地が復元される
10. 鶏小屋を購入
11. 加工場用地を購入
12. 製粉機を建設
13. 生産途中で保存
14. 再読み込み
15. 予約原料・残り時間・出力が二重化しない
16. 集配ボックスへ資源を入れる
17. 集配スタッフが運搬中に保存
18. 再読み込み
19. 資源を失わず安全な地点から再開
20. JSON書き出し
21. 新規状態へ変更
22. JSON読み込み
23. 元の状態へ戻る

PCとスマートフォンの両方で、最低1回ずつ実施してください。

# 5. 自動テスト

## 保存値の型

- 整数在庫は小数を拒否
- 小数ミリ秒の時間値は正常化または受理
- NaNを拒否
- Infinityを拒否
- 負数を拒否

## round trip

- snapshot作成
- envelope作成
- repository保存
- repository読込
- checksum検証
- migration
- restore
- 再snapshot
- 重要フィールド一致

## 加工場

- 前提不足を明示
- 東農地だけでは解放不可
- 鶏小屋だけでは解放不可
- 両方解放で購入可能
- 800コイン未満で購入不可
- 購入時に正確に800減る
- 二重購入不可
- 製粉機建設
- ベーカリー前提
- 生産cycle
- 保存・復元

## UI導線

- 解放通知が一度だけ
- 次の目標が更新される
- 案内ボタンが加工場を指す
- 未解放加工場が完全非表示にならない
- 操作範囲と表示範囲が一致
