# v0.9.8 根本原因調査

この文書は、v0.9.7 `main`（調査基準SHA `4c69de9a04a22e3086dd64ce2a447f18e4dd538e`）で確認した実装上の主因を記録します。

## 1. 牛舎の状態と操作場所が分からない

`DairySystem.draw()` は牛舎本体を描画しますが、実際の操作は固定座標で判定されています。

```text
干し草投入: おおむね (3320, 1360)
牛乳回収:   おおむね (3520, 1360)
```

ところが、干し草台とミルクタンクを明確に区別する設備表示、現在量、必要量、入力・出力矢印がありません。

実ランタイムの生産規則は `advanceCows()` にあり、

```text
牛1頭
干し草1個を消費
10秒生産
牛乳1個
```

です。

この規則も世界表示や管理画面に現れていません。現在のHUDは「牛・草・乳」の短い数値だけで、次の牛乳までの時間、稼働中の牛、餌待ち、タンク満杯を説明しません。

## 2. 倉庫の干し草が牛舎へ到達しない

牛が参照するのは `state.dairy.hayRack` だけです。

手動投入も、

```ts
state.cargo.amounts.hay
```

から1個ずつ干し草台へ移すだけで、`state.barn.hay` は参照しません。

一方、次の基盤はすでに存在します。

```text
dairy.dairyWorker
dairy.workshopWorker
selectDairyTask(...)
```

しかし、`DairySystem` はこれらを実ランタイムで更新していません。したがって、倉庫へ入れた干し草を牛舎へ運ぶ自動経路がなく、酪農スタッフ状態も保存されるだけです。

## 3. 加工場は倉庫供給ロジックを持つが、利用導線が欠ける

`ProcessingWorkerSystem.runBatch()` は、雇用済みスタッフがいれば、

- 製粉機・ベーカリーの完成品を倉庫へ移す
- 倉庫から機械入力へ原料を運ぶ

処理を持っています。

しかし、スタッフを雇用する操作がありません。

`UIScene` の「スタッフ」ページはカードを表示するだけで、雇用・研修ボタンを作っていません。`ProcessingSystem.handlePanelAction()` も機械の運転モードしか受け付けません。

さらに表示値もauthoritativeではありません。

```text
UIの研修費:
260 / 620コイン相当の固定表示

実ロジック:
製粉スタッフ 420 / 900
製パンスタッフ 650 / 1300

UIの容量:
4 + level × 2

実ロジック:
製粉スタッフ 8 / 12 / 16
製パンスタッフ 6 / 9 / 12
```

このため、スタッフ欄は操作不能なだけでなく、表示値も実ロジックと一致しません。

## 4. 集配所の建設進捗が何周も回る

`CollectionNetworkSystem.updateConstruction()` は、建設範囲に入ると、可否を確認せず進捗を加算します。

```text
1200ms到達
→ buildCollectionFacility(...)
→ 失敗しても holdMs を0へ戻す
→ 範囲内なので再び0%から進む
```

前提施設がない場合、コインが足りない場合、すでに建設済みの場合でも同じです。

`getCollectionFacilityAvailability()` は存在しますが、進捗開始前のゲートとして使われていません。また、成功・失敗後に再実行を止めるarmed状態もありません。

## 5. 麦畑拡張後に作物と地面が一致しない

麦畑の作物は、購入直後に `configureWheatNodes(level)` で30→42→54へ更新されます。

一方、畑の土・畝・柵は `createFarmWorld(scene, wheatLevel)` でシーン生成時に一度だけ描かれます。購入後に再描画されません。

そのため、

```text
作物ノード: 新しいlevel
畑グラフィック: ゲーム開始時のlevel
```

となります。

さらに `getActiveWheatBounds()` は幅を `[430, 595, 760]` と固定し、実際のノード中心と見た目の半径から導出していません。拡張区画境界と追加列の位置を別々に編集できる構造です。

論理上の株数30・42・54は正しいものの、表示はauthoritativeではありません。

## 6. 麦運搬スタッフが一時集荷箱で停止し得る

`WorkerSystem.updateTransporter()` は、積込が成功した直後にだけ、

```text
carried >= 固定容量6
```

を確認して倉庫へ向かいます。

しかし、積込前に既に容量以上を持っている場合、

```text
loadTransportWorkerOne(...)
→ changed = false
```

となり、その後の遷移がありません。箱が空になるまで `loading` に残ります。

プレイヤーが箱を手動で空にすると、別分岐の、

```text
crate <= 0 && carried > 0
```

が成立して、初めて倉庫へ向かいます。報告された挙動と一致します。

また、実ランタイムは研修レベルにかかわらず固定値を使っています。

```text
容量 6
移動速度 185
積込・荷下ろし150ms
```

authoritativeなレベル別値は既に、

```text
容量 6 / 8 / 10
```

として `getWheatWorkerRuntimeParameters()` に存在します。

## 7. 倉庫納品が一個ずつ

`GameScene.tryUnload()` は、倉庫範囲内で、

```ts
unloadNextCargoOne(...)
```

を180msごとに一回呼びます。

12個なら12回、24個なら24回待ちます。複数資源を持つ場合も同様です。

## 8. 集配ボックスの預入・取出が一個ずつ

`CollectionNetworkSystem.updatePlayerTransfer()` は、

```text
預入 130msごとに1個
取出 150msごとに1個
```

です。

純粋関数も、

```text
depositPlayerResourceOne
withdrawPlayerResourceOne
```

だけです。

契約納品と売上回収はv0.9.7で一括化済みですが、通常倉庫と集配ボックスは旧式の逐次処理のままです。

## 修正原則

v0.9.8では、次を共通原則にします。

1. 可否を判定してから進捗を開始する
2. 一回の意図的操作は一回の論理取引にする
3. 表示値、費用、容量、座標はauthoritativeな純粋定義から取得する
4. 商品移動は必ず移動前後の保存則を検証する
5. 既存の保存状態を捨てず、停止状態から自己回復する
6. 見た目と当たり判定を別々にハードコードしない
